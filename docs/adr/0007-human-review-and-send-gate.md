# ADR 0007: Human review loop and send gate

- Status: Accepted (amended 2026-10-29: change requests reduced from 3 to 2; summary text cannot be edited directly)
- Date: 2026-10-29

## Context

Email may only be sent after human approval. Approving must send exactly the approved version, and rejecting must send nothing. Any change to the content or the recipient needs approval again. Approval and delivery status must be recorded.

## Decision

1. **What the review screen shows.** Amended 2026-10-30.
   - **The email to be sent:** recipient, subject, and a body containing:
     - the question and the interpreted intake form
     - the summary
     - a short **Limitations** section
     - the compact evidence table with citations
     - the footer
   - **Reviewer notes (not sent):** every warning (removed claims, unverified details, Critic issues, an unavailable Critic, an unavailable source, a missing comparison), shown after the email and outside it, so the reviewer sees them before approving. They are kept in the run file and never sent.
   - **The Limitations section:** code builds it from the run state, using fixed sentences for three cases only:
     - a source was unavailable
     - no synthesis could be produced
     - there is no cross-study comparison

     It contains no LLM wording, no removed-claim text and no internal details. If none of the three cases applies, there is no Limitations section. Missing confidence intervals and p values are stated in the summary claims instead (summarizer prompt).
   - **What the fingerprint covers (ADR 0013):** exactly the email that is sent: recipient, subject and body. Reviewer notes are not part of the email, so they never change what is approved or sent.
   - **Compact evidence table:**
     - **Included studies:** their key evidence fields, each with its quote.
     - **Needs-review records:** one line each, naming the missing detail.
     - **Excluded records:** one line each, giving the failed rule with its supporting quote or metadata.

     The full per-record details are kept in the run file only. Amended 2026-10-30, because the full table made the review screen too long to read.
   - **Display rules:** the screen is shown once, and shown again only after an edit changes the email. An invalid choice prints only "Please choose a, r, e, s or c", without reprinting the screen.

2. **Defaults.** The recipient defaults to the user's own address, taken from config. The subject is generated by code from the question, the date and the run ID. The body ends with a footer that code generates, containing the run ID (ADR 0013).

3. **Choices on every review.** Approve, reject or request changes.

4. **Request changes.** The human writes an instruction. That instruction goes to the Summarizer, and the new draft passes through the content checks (ADR 0005) and the Critic, with a fresh budget (ADR 0006). It then returns to human review. A human instruction cannot get around the grounding checks.

5. **Limit on change requests.** Request changes is allowed twice. On the third review, only approve or reject are offered.

6. **No direct edits to the summary text.** The human cannot edit the summary text by hand. This is listed in the README as a future improvement.

7. **Recipient and subject.** The human can edit these directly at review. These edits do **not** go back to the Summarizer. The review screen shows the updated email again and asks for approval.

8. **Any change needs approval again.** This covers content, recipient and subject.

9. **The approval log records** one of `approved`, `approved_with_warnings` or `rejected`.

10. **The send function will not run** without a recorded approval of exactly the content being sent.

## Why

- Sending email cannot be undone, so the decision belongs to a person and is enforced by code, never by an LLM.
- Changes to the summary go back through the same pipeline, so a human edit cannot add unsupported claims.
- Recipient and subject are not evidence, so editing them does not need the Summarizer. They still need fresh approval, so the approved version is always exactly what gets sent.
- The cap on change requests guarantees that review ends.
